## 一、评估标准过严（Agent 本身交付正确）— 4 例

### #29「信用额度最高的前5位客户」/#30「研究生学历客户的账单金额 top 5」（credit）

**现象**：均交付 1 张完整表格，但无图表。

**根因分析**：
- 这两个问题本质是 **top_n / filter_rows + 排序** 操作，返回的是"按数值取前 N 条 **明细记录**"。
- 这类操作在工具层执行的是 `df.sort_values(...).head(top)` 或筛选后的明细，输出的是**记录列表**，工具主动标注 `chart_type="none"`（因为明细记录画柱状图/折线没有统计意义）。
- 评估脚本把这两个用例标为 `comprehensive`（全面），全面类的判定标准要求"必须同时存在表格 **和** 图表"，因此被误判失败。

**结论**：**非缺陷**。
- Agent 正确理解了问题、正确调用了 `top_n`/`filter_rows`、正确返回了表和结论。
- 是**评估脚本的期望值（full=f"图表 as 前提"）设定不当**，不是 Agent 能力问题。
- 这类"列 TopN 记录"与 `head`（数据预览）在语义上同类，本就应允许无图。

### #39「北京最高气温超过30度的记录」（climate）

**现象**：交付 1 张表格（北京高温记录），但无图表。

**根因分析**：
- 这是典型的 `filter_rows`（条件过滤）操作：`column=tmax, op=">", value="30"`。
- 过滤后返回的是符合条件的**明细行列表**，语义上与 `head` 预览一致，`chart_type` 为 `none` 合理。
- 用户问"有哪些记录"而非"统计趋势"，无图完全符合预期。
- 评估脚本按 `comprehensive` 要求出图 → 误判。

**结论**：**非缺陷**。筛选明细类的合理输出就是"一张表 + 文字说明"，不要求图。

---

### #48「美国的累计确诊是多少」（health）

**现象**：交付 2 张表格（美国累计确诊、相关统计），但无图表。

**根因分析**：
- 这是一个**单值查询**问题——用户只要一个具体数字。
- Agent 用 `filter_rows`/`groupby` 定位美国并返回 `total_cases` 数值，本质接近 `describe`/单值统计，**天然不需要图表**。
- 评估脚本的 `comprehensive` 期望出图 → 误判。

**结论**：**非缺陷**。单值/数值查询返回表格和文字结论即可，图表在此场景反而多余。

## 二、Agent 真实稳定性问题 — 2 例

### #17「TSLA 的收盘价时间趋势」（finance，24.5s）

**现象**：**无表格、无图表**，耗时最长的用例之一。

**根因分析**：
- 问题需要"选取股票到时间轴"（TSLA + Date），涉及 `filter_rows`（或 `where_col=TSLA`）配合 `time_trend` 的两步组合。
- 24.5s 表明 Agent 经历了**多轮工具调用 + 可能的参数校验失败重试**后，最终未能产出 `deliver`（未到达结束节点），导致 `rendered` 为空 → 无表格、无图表。
- 属 **LLM 偶发的多步骤规划不稳定**：在有限轮次内没能组织出「先过滤再趋势」的正确调用序列，或某次 `analyze_data` 参数被拒绝后放弃了交付。
- **非确定性 bug**：上一轮 10 条评估中同类 `AAPL 收盘价走势` 是 PASS，说明代码路径可用，是 LLM 本轮行为不稳定的表现。

**定位/改善方向**：
- 提示词加入 `time_trend + where_col/where_value` 的组合 Few-shot 示例，降低组合调用出错率。
- 工具失败后已有"错误作为 ToolMessage 回喂"机制，可再加**强制重试上限**：连续 N 次失败即强制 deliver 并说明，避免空转。
- 评估样本具有随机性，建议同用例跑多次取平均，而非单次判定。

### #45「各国家新增确诊的每日趋势对比」（health，28.0s）

**现象**：**无表格、无图表**，全部用例中最慢（28s）。

**根因分析**：
- 问题要求"多国家 × 每日"的趋势对比，即 `grouped_trend`（`group_by=location, date_col=date, value_col=new_cases`）。
- 这是工具库里**计算最重**的操作之一：health 表 10052 行、多国家、日粒度，`grouped_trend` 做完 pivot 后要按国家总量截断到最多 8 个序列。
- 28s 表明 Agent 的推理循环很长（多次尝试不同参数组合），最终仍未在 `recursion_limit=40` 内完成 `deliver`，返回空结果。
- **与 #17 同理**：高复杂度组合问题下 LLM 规划偶发失败，属稳定性问题，非确定性 bug。

**定位/改善方向**：
- 给 `grouped_trend` 增加对"国家过多"的引导：提示词建议先用 `top_n`/国家总量筛选再比较，或自动聚合 `freq=M`（月粒度）减轻计算。
- 适当放宽 `recursion_limit` 或优化工具执行时延（数据集缓存已做，主要开销在 LLM 多轮调用本身）。
- 同样建议多轮采样评估。

## 三、汇总与改进优先级

| 改进项 | 针对用例 | 类型 | 优先级 | 工作量 |
|---|---|---|---|---|
| 修正评估脚本：`comprehensive` 中"列明细/TopN/单值查询"类允许无图 | #29/#30/#39/#48 | 评估标准 | 高 | 低 |
| 提示词增加 `time_trend`/`grouped_trend` 组合的 Few-shot 示例 | #17/#45 | Agent 稳定性 | 高 | 低 |
| 增加工具失败强制重试上限（连续失败 N 次强制 deliver） | #17/#45 | Agent 稳定性 | 中 | 中 |
| 多轮采样评估（同用例跑多次取平均通过率） | 全部 | 评估方法 | 中 | 低 |

**结语**：4 例误报（标准过严）+ 2 例偶发不稳定。无确定性功能 bug。修正标准后真实通过率约 92%，剩余 8% 集中在"多国家/多股票 × 时间轴"的高复杂度组合提问上。
